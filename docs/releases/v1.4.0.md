# Darkside v1.4.0

## `/order66` — Configuração de modelos e execução externa mais robusta

Melhorias focadas na confiabilidade da orquestração multi-agente e na precisão dos agentes externos (Reasonix e Kimi).

---

### Tabela de configuração de modelos

O `/order66` agora documenta explicitamente qual modelo usar em cada fase:

| Fase | Agente | Modelo |
|------|--------|--------|
| Phase 1 — Order | engineer, security | `opus` |
| Phase 2 — Tasks | — | `sonnet` |
| Phase 3 — TDD | tdd | `sonnet` |
| Phase 4 — Code | coder | `sonnet` |
| Phase 5 — Review | reviewer | `sonnet` |

Quando subagentes são usados via Agent tool, o parâmetro `model` deve ser passado explicitamente. Nas fases executadas inline, o modelo do orquestrador é herdado.

---

### Restrições obrigatórias no prompt de delegação

Todo prompt enviado para agentes externos (Reasonix ou Kimi) agora exige três blocos de enforcement:

- **Scope restriction** — instrui o agente a implementar **apenas** o que está nas tarefas, sem adições, refatorações ou melhorias fora do escopo.
- **Status reporting** — formato padronizado de progresso por tarefa (`[TASK N/TOTAL] ✅ ...`) e resumo final (`[ORDER66 COMPLETE]` ou `[ORDER66 INCOMPLETE]`).
- **Git prohibition** — proíbe explicitamente `git add`, `git commit` e `git push` — decisão exclusiva do usuário.

Além disso, as instruções completas dos sith-agents `tdd.md` e `coder.md` agora são incluídas no prompt com diretrizes de persona explícitas, garantindo que o agente externo siga exatamente as convenções do projeto.

---

### Reasonix — modelo fixo `deepseek_v4_pro`

O comando de execução agora inclui `--model deepseek_v4_pro` obrigatoriamente, tanto na execução inicial quanto nas correções:

```bash
reasonix run --dir "<project_dir>" --output-format json --permission-mode auto --model deepseek_v4_pro --allowed-tools "Bash(test commands matching project stack)" "<prompt>"
```

O nome exibido na seleção foi atualizado para **Deepseek V4-Pro (reasonix)**.

---

### Kimi — prompt via arquivo e modelo `k2-0725-coder-basic`

O fluxo do Kimi foi completamente revisado. O CLI não aceita prompts inline como argumento posicional — o prompt deve ser salvo em arquivo e passado via `-p`:

```bash
# 1. Salvar prompt em arquivo
/tmp/kimi-order66-prompt.txt

# 2. Executar
kimi -p /tmp/kimi-order66-prompt.txt --yolo --model k2-0725-coder-basic
```

Correções usam o mesmo padrão com `--continue`:

```bash
kimi -p /tmp/kimi-order66-correction.txt --continue --yolo --model k2-0725-coder-basic
```

O nome exibido na seleção foi atualizado para **Kimi K2.7 Coding (kimi)**.

## `/probe-droid` — Nova skill de QA não-técnico

Nova skill para gerar casos de teste em linguagem de produto a partir do diff de uma branch — sem jargão técnico, sem nomes de arquivo ou função, sem trechos de código.

### Como funciona

1. **Seleção de branch** — branch atual, nome de branch específica, ou link/ID de card (o agent encontra a branch relacionada)
2. **Investigação do diff** — lê as mudanças e determina a **intenção** de cada alteração a partir do card, commits e contexto (não do código em si)
3. **Geração dos casos de teste** — um caso por mudança observável pelo usuário, com Scenario, Steps e Acceptance Criteria orientados à intenção, não à implementação
4. **Salvamento** — notas salvas em `.darkside/probe-droid/YYYY-MM-DD-<nome>-qa-notes.md`
5. **Envio ao card** — se um card relacionado for detectado e um MCP compatível estiver disponível (Jira, GitHub, Businessmap, Trello, ClickUp, Asana, Azure Boards, Linear), oferece postar as notas como comentário

### Plataformas suportadas para envio

| Plataforma | Formato |
|------------|---------|
| Jira, GitHub, Trello, ClickUp, Linear | Markdown |
| Businessmap, Asana, Azure Boards | HTML |

## `/moff` — Nova skill de gestão de projeto

Assume o papel de Product Manager do projeto. Cuida do que nenhuma outra skill cuida — o contrato de expectativa, o backlog e seu sync com o tracker, as métricas e o registro de cada mudança de combinado. Todo o resto é delegado por nome para as skills do plugin.

### Forma do projeto

O setup começa declarando duas coisas, e todo o resto se ramifica a partir delas em vez de assumir:

| | Opções |
|---|---|
| **Quem recebe** | Cliente externo · Stakeholder interno · Ninguém além de você |
| **Quem executa** | Você sozinho · Time pequeno (2–4) · Time com papéis dedicados |

Sob receptor "ninguém", não há contraparte: o modo Renegociar fica indisponível e `§3` vira a sua própria cadência de revisão.

### Cinco modos

| Modo | O que faz |
|------|-----------|
| **Setup** | Conduz o charter em 10 passos — critérios verificáveis de sucesso com exclusões nomeadas, contrato de comunicação, capacidade e orçamento de governança, gitflow, fluxo de desenvolvimento, métricas e riscos |
| **Planejamento** | Agrupamento, quebra de estórias, cards executáveis, **ordem de execução** e sync com o tracker com reconciliação de volta |
| **Execução** | Roteia um card pela esteira — as outras skills fazem o trabalho, o Moff checa os portões e registra o resultado |
| **Relatório** | Uma janela declarada (`weekly`, `sprint`, `monthly`, `milestone`, `project-to-date`), explicando em três linhas o que cada card fechado nela realmente entregou |
| **Renegociar** | Posição, alternativas que mantêm a expectativa atendida, e o log de negociação |

O modo é **inferido do estado do projeto**, não perguntado por menu: card em progresso → Execução; cerimônia em 24h sem relatório → Relatório; backlog vazio → Planejamento. Uma palavra do usuário sobrescreve.

### Ordem de execução — dependência primeiro, espera nunca na frente

Os cards são puxados numa ordem **derivada**, não sentida: dependências duras, depois o card que prova a premissa, depois valor demonstrável, e empate desempatado pelo menor.

Cards de **espera longa** — janela de monitoramento, aprovação externa, provisionamento de terceiro — são disparados cedo e **nunca ocupam a fila**: dispara, registra o que está sendo esperado, e puxa o próximo card na mesma sessão. Colocar "monitorar por duas semanas" na frente de tudo compra duas semanas em que nada é construído.

**Ordem não é prioridade.** Ordem responde *o que vem agora* e vive no rank do board; prioridade responde *quanto custa atrasar* e vive no campo `Priority`. Um card de espera longa costuma ser prioridade alta e ordem tardia — juntar os dois é exatamente o que põe o card errado no topo do board.

### Decisões em aberto

O charter tem uma `## 11. Open Decisions` que não existe nas outras skills: é o que impede uma pergunta sem resposta de parecer idêntica a uma respondida. Enquanto houver linha lá, o cabeçalho fica `⚠️` com o número contado — o `✅` só chega quando a seção esvazia.

### Guardrails

- **Git é só proposta** — nunca roda `add`, `commit`, `push`, branch, tag ou PR. Propõe; você executa
- **O tracker é operacional** — cria, move, comenta e atualiza livremente; escrita em lote é previewada em bloco único, ação destrutiva é confirmada individualmente
- **Deploy exige ordem explícita**
- **Não lido é não lido** — nenhuma métrica, fato ou estado do tracker é preenchido por inferência

Salva em `.darkside/moff/`.
